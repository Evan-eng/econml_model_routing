# Required paper changes for submission v44

This checklist compares `econml_model_routing_submission_v44.pdf` with the
accepted Qwen3-8B artifacts published in this repository. It covers changes to
the paper and submission package only. The accepted experimental design,
reported accuracy values, corrected scorers, and statistical conclusions do
not require rerunning training or evaluation.

## 1. Expand the GPU and runtime disclosure in Appendix A.4

Replace the sentence "Each arm uses one NVIDIA GPU" with a description of the
accepted resource contract:

> Training and GPU evaluation ran on Georgia Tech PACE ICE as independent Slurm
> tasks with one NVIDIA HX00 GPU per task. The primary capability-mixture run
> used H100 allocations; robustness recovery used H100 or H200 allocations.
> Each GPU task requested eight CPU cores, 224 GiB of host memory, 50 GiB of
> node-local scratch, and a maximum of 15 hours 30 minutes per attempt. The
> terminal allocation ledgers retain successful, failed, retried, diagnostic,
> and cancelled allocations.

Do not describe the 224 GiB Slurm request as GPU memory. It is host memory
allocated per GPU task.

Add the accepted aggregate GPU-hours and wall-clock/runtime summary from the
terminal `compute_summary.json` files in
`accepted-full-export-qwen3-8b-confirmatory-20260828.zip`. Do not use the
85.135833 GPU-hour partial total in `LOGBOOK.md`; that was recorded before
terminal reconciliation. Separately identify CPU-only MBPP rescoring time.

## 2. Revise checklist question 8 (compute resources)

Keep the answer as **Yes** only after adding the concrete hardware, host-memory,
scratch, per-attempt limit, per-arm runtime range, and terminal aggregate
compute to the paper or supplement. State that total project accounting includes
failed and superseded operational attempts, as requested by the checklist.

Suggested justification:

> Appendix A.4 and the accepted artifact report the PACE ICE worker type,
> H100/H200 allocation classes, eight CPU cores and 224 GiB host memory per GPU
> task, 50 GiB node-local scratch, per-attempt time limits, per-arm training and
> evaluation runtimes, CPU rescore time, and terminal aggregate allocation-only
> compute. The ledgers retain failed, retried, diagnostic, and cancelled jobs.

## 3. Correct the open-access and redistribution statement in checklist question 5

The current justification says that public datasets are downloaded at pinned
revisions "rather than redistributed." The published 57 GB source-run tree also
contains prepared `math_train.jsonl`, `code_train.jsonl`, `eval_math.jsonl`, and
`eval_code.jsonl` caches. Replace that sentence with:

> The artifact pins the upstream model and dataset revisions. It does not
> duplicate the Qwen3-8B base weights, but the complete source-run export does
> include the prepared training and evaluation JSONL caches used by the run,
> together with provenance and upstream license information.

Retain **Yes** only if the artifact used for review is actually accessible to
reviewers and includes instructions for obtaining its Git LFS objects.

## 4. Correct checklist question 11 (released models and safeguards)

The current statement that the paper releases "no trained model" is false for
this repository. It publishes all 45 final QLoRA adapters and two retained
adapter checkpoints per arm, plus optimizer and scheduler state. The base
Qwen3-8B weights are not duplicated.

Suggested replacement:

> The artifact releases experiment-produced QLoRA adapters and checkpoints
> derived from the public Qwen3-8B base model, but not the base-model weights.
> These adapters reproduce controlled math/code allocation experiments and do
> not add a general-purpose capability or a scraped private dataset. We assess
> their incremental misuse risk as low; generated-code evaluation remains
> documented as requiring a network-isolated sandbox.

The answer may remain **N/A** only with this accurate qualification. Otherwise
answer **Yes** and describe the sandbox and release rationale as safeguards.

## 5. Narrow the "every table" reproducibility claim in Appendix A.4

The repository reproduces the raw experiment analysis and figure, but it does
not currently contain a tracked command that directly creates the
manuscript-facing `all_profile_means` and `confirmatory_results` tables. Because
no additional table-generation script is being added, replace:

> commands for reproducing every table

with:

> commands for reproducing the core training, evaluation, rescoring, and
> analysis outputs, together with the accepted manuscript-facing tables and
> their underlying machine-readable results

Do not claim that every typeset table is regenerated by one command.

## 6. Correct Appendix A.9's numerical-artifact claim

`routing_innovation_sim.py` is not present in this repository or the available
Overleaf source archive. Until that file and its generated CSV grids are
available, remove the claim that an "accompanying single-file Python artifact"
and executable self-test command are supplied.

Replace the opening and command with wording such as:

> We numerically checked the listed identities and comparative statics using a
> NumPy and Matplotlib implementation. The numerical checks generate the grids
> underlying Figure 1 and the post-threshold example below.

Do not print `python routing_innovation_sim.py --self-test --output-dir results`
unless that exact file is included in the submitted artifact. Alternatively,
package the theoretical code as a separate supplement and name that supplement
explicitly.

## 7. Resolve artifact anonymity

The GitHub publication receipt records the origin
`https://github.com/Evan-eng/econml_model_routing`. That is not anonymous. If
this repository is the review artifact, publish an anonymized snapshot without
the identifying origin/receipt and use that snapshot for the paper's
"anonymized accompanying artifact" claim. If a separate anonymous artifact is
already being submitted, no paper-text change is needed, but verify that the
paper points only to that artifact during review.

## 8. Resolve release licensing before retaining checklist question 12 as Yes

Appendix A.4 records the upstream model and dataset licenses, but this repository
does not currently have a top-level license covering the authors' code and
newly published materials. The authors must choose that license; it should not
be inferred automatically. Add the chosen license and any required notices to
the release package, or qualify checklist question 12 to say that upstream
licenses are documented while the repository's release license is pending.

## 9. Keep the following v44 statements unchanged

The following already match the accepted artifacts:

- the full paper title;
- "prespecified rather than preregistered" and the reason for that distinction;
- the 45-arm, nine-share, five-seed design and all frozen hyperparameters;
- every reported Table 1 accuracy after rounding;
- the four confirmatory robustness profiles and descriptive status of the other
  42 profiles;
- the corrected MBPP and strict symbolic MATH-500 metric audit;
- the stationary-share interval, failed admissibility conditions, and decision
  not to interpret the generalized threshold;
- the limitation that the experiment identifies training effects rather than
  provider investment, R&D response, or equilibrium behavior.

## 10. Final consistency pass

Before uploading the next PDF and supplement:

- search the paper and supplement for `preregistered` and use `prespecified`
  for this experiment;
- verify that the paper title matches the repository title exactly;
- verify that all artifact file names, SHA-256 digests, and counts still match
  the submitted archives;
- preserve the original receipt-bound analysis figure in the canonical archive
  and treat its threshold histogram as a diagnostic rather than an interpretable
  threshold interval;
- do not change any accepted numerical result merely to accommodate the revised
  presentation.
